01 /

共通の運営基盤CONTROL PLANE / CANONICAL RULES

記録や手順ごとに、基準となる元ファイルを決めています。一覧や図は、その参照先を案内するものです。下の名称は実際のフォルダ・ファイル名です。

記録を中心に、人とAIが作業する。

記録の本体はMarkdownなどのファイル。Obsidianは閲覧・編集の場、GitHubは同期・変更履歴・変更提案の基盤です。

SYSTEM LAYER
_system/共通の手順と定義

skillsに作業手順、referenceに構造・設計判断を置く。AIごとの入口からも、この共通基準を参照する。

index.md情報の所在を探す地図

AI向けのVault全体マップ。短い説明から必要な元ファイルへ進む入口であり、詳細な記録の本体ではない。

project-overview.md現在の仕事の案内板

各Workの元ノートを参照する俯瞰用の一覧。進捗・状態の基準は各ノートの属性情報にあり、一覧自体が正本ではない。

Obsidian：閲覧・編集GitHub：履歴・変更提案AI：手順に沿う作業人間：目的・承認・評価

AIが担うこと：必要な記録を参照し、規定の手順（skill）に沿って整理、下書き、更新案の作成などを行います。許可された可逆な内部変更は委任し、承認が必要な操作は各業務の規約に従います。たとえば記事の下書きと公開は別で、noteへの公開にはオーナーの明示が必要です。判断できない条件や不明な数値を、AIが推測で補わないルールを設けています。

02 /

仕事を6つの種類で管理WORK PORTFOLIO / ACTUAL VAULT FOLDERS

Workは、制作や運営などの管理対象を指します。終わり方と役割に応じて6種類に分け、それぞれのフォルダへ置きます。下はVault全体のツリーではなく、Work分類に使う6つの保管先です。

Grownbox

grownbox/
育成中の企画・研究

まだProject化していない企画・研究。仮説を育て、有限の仕事として進めるか判断する。

Projects

projects/
完了条件のある仕事

完了条件のある制作・開発・展示。進捗と次のアクションを追跡する。

Series

series/
作品を生み続ける親シリーズ

複数の作品や活動を継続して生むシリーズ。親単位に完了率は付けない。

Services

services/
継続して運営する仕組み

サイトやアプリなど、継続運営を前提とする仕組み。開発中・本番運用・保守などの段階で管理する。

Collections

collections/
項目を足していく棚

完了条件を持たず、必要な項目を追加していく棚。項目の収録状態で捉える。

Resources

resources/
再利用する方法論・知識

方法論・知識・共通設計を保存し、別の制作でも使えるようにする。作業の進捗は管理しない。

分類（kind）、状態（status）、必要に応じた段階（stage）は別の情報です。0〜100の進捗値はProjectだけが持ち、継続Serviceには完了率を付けません。

ローンチ担当者から見ると：「特定のリリースを受入条件まで仕上げる」はProject、「公開したサービスを保守・改善し続ける」はServiceに当たります。これは分類の説明例であり、公開時にフォルダが自動で切り替わる仕組みではありません。

03 /

制作から公開・運営への流れBUILD → LAUNCH → LEARN LOOP / BUSINESS VIEW

これは業務の関係を説明する概念図です。フォルダの階層や、自動処理の順序ではありません。記事の下書き、Work更新、解析記録などには個別の手順がありますが、以下の5段階を一括で自動実行する仕組みを示してはいません。

1

発見・企画を育てるDISCOVER / FRAME

思いつきや現場の困りごとを記録し、仮説と実行条件を整理する。

grownbox/inbox/resources/
2

作る・検証するBUILD / VALIDATE

完了条件のある制作はProjectで管理し、設計・検証の記録を残す。コードの実装は各リポジトリや開発環境で進める。継続Serviceでは、開発・運営・改善の段階を記録する。

projects/GitHub PRAI skills
3

公開・届けるLAUNCH / DISTRIBUTE

記事の下書きや公開用素材を整え、各媒体の手順と必要な承認を経て公開する。サイトや配信ツールの実装・稼働は別の環境が担い、Vaultは記録と手順を支える。

note-workspace/services/site / apps / SNS
4

公開後の反応と収支を確かめるMEASURE / DECIDE

閲覧・流入などは取得期間と取得時点を伴う観測記録として扱い、実際の金銭の動きとは区別する。不明値をゼロで埋めず、人間が継続・改善を判断する材料にする。

analytics_view/Finances/
5

知識・部品・経験を次へREUSE / COMPOUND

制作で得た方法や知識をResourcesへ整理する。項目を集めるならCollections、個別作品を継続して生む活動ならSeriesと、再利用の役割に応じて扱う。

resources/collections/series/
↺ 学びを次の企画へ ─ 記録を読み直し、次に試すことを判断する。

05 /

完了・休止・中止した仕事を保管するLIFECYCLE / COLD STORAGE

cold-storage/ は、現役の管理対象から外したWorkの保存場所です。7つ目の分類ではなく、元の分類を保ったまま状態別に保管します。AIも通常の開始時には読みません。

完了・役割終了cold-storage/archive/

完了・役割終了。実績と学びを残す。

休止・再開待ちcold-storage/freezer/

一時停止。再開の意志があるもの。

中止・廃案cold-storage/graveyard/

復活を前提にせず、判断の履歴を保存。

通常の archive/ は、Work以外の古い記録・一般ノート・退役したガイドなどを保管する別領域です。Cold StorageのArchiveから現役へ戻す際は、現在の目的や条件を確認し直します。

THE YZRS PRINCIPLE

思いつきを形にして、
公開し、確かめる。
次に使える記録を残す。

この構成の強みは、記録の元ファイルと手順を共有しながら、制作・公開・運営を別の責務として扱えることです。集計表の再生成や記録の整合チェックは個別のスクリプトで支援しています。一方、検出した食い違いの修正、公開判断、実機や利用者による評価は必要です。自動化の範囲や検証状況は手順・実行環境ごとに異なります。
